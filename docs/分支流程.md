# 分支流程

本文件说明 MATR 的分支模型、日常协作方式与发布路线。目标是让外部贡献者和 fork 有明确的贡献基线，同时保证 `main` 在任何时刻都可直接打包发布。

## 分支模型

| 分支 | 用途 | 推送权限 | 生命周期 |
|---|---|---|---|
| `main` | 稳定发布线。只接受来自 `develop` 的发布合并和 `hotfix/*` 的修复合并，每个正式版在此打 tag | 仅维护者合并，禁止直接 push | 长期存在 |
| `develop` | 默认分支与集成线。所有功能、修复和外部 PR 的默认落点 | 维护者可直接合并 | 长期存在 |
| `feat/<feature-name>` | 新功能或较大改造 | 创建者 | 合并后删除 |
| `fix/<scope>` | 常规缺陷修复 | 创建者 | 合并后删除 |
| `hotfix/<scope>` | 已发布版本的紧急修复，从 `main` 切出 | 维护者 | 合并后删除 |

三条顶层规则：

- 每个正式版发布后（含热修合回）`main` 与 `develop` 应回到同一提交，不允许长期分叉；测试版期间允许 `develop` 领先于 `main`。
- `main` 上不做日常开发，任何未经验证的改动都不进 `main`。
- 正式版 tag 只打在 `main` 上，测试版 tag 打在 `develop` 上。MirrorChyan 依据 tag 名推断发布频道：正式版先用 PR 合并进 `main` 再打 tag，测试版直接在 `develop` 打 tag 发布，不必每个测试版都对 `main` 开 PR。

## 首次搭建

本节记录从单 `main` 迁移到双主干时执行的操作，仅在仓库首次切换时需要。

1. 确认 `main` 的收尾改动已全部提交并推送，工作区干净。
2. 从当前 `main` 建立 `develop` 并推送。

```
git switch main
git pull --ff-only
git switch -c develop
git push -u origin develop
```

3. 在 GitHub 仓库设置中把默认分支改为 `develop`。切换时 GitHub 会把尚未合并的 PR 目标分支自动改到 `develop`，操作前先确认当前开放的 PR 清单。
4. 按下一节的规则配置分支保护。
5. 把 `upstream` 远端的 push 地址改为不可推送，避免误推上游的 MFAAvalonia 仓库。

```
git remote set-url --push upstream no_push
```

## 分支保护规则

| 分支 | 规则 |
|---|---|
| `main` | 禁止直接 push；必须通过 PR 合并；禁止 force push；禁止删除 |
| `develop` | 允许维护者直接合并；禁止 force push；禁止删除 |

当前 `main` 不要求 review。GitHub 不允许批准自己开的 PR，仓库只有一个维护者时要求 review 会导致自己的 PR 永远无法合并；等有第二个协作者后再把 Required approvals 设为 1。`develop` 同样不强制 review，以保留维护者处理小改动和合并自己分支时的效率；外部贡献者的 PR 仍然需要 review 后再合并。

`main` 因为要求通过 PR 合并，本地先合并再推送的方式会被远端拒绝。发布和热修都必须走 GitHub PR。

## 日常开发流程

### 新增功能或常规修改

从 `develop` 切出短分支，完成后以 PR 合回 `develop`。

```
git switch develop
git pull --ff-only
git switch -c feat/<feature-name>
```

即使改动由维护者本人完成，也应走短分支，避免半成品直接堆积在 `develop` 上。

PR 描述至少写明以下几点：

- 改动范围与目标，涉及的任务 pipeline 或源码文件。
- 验证方式与实际验证结果；涉及平台相关改动时说明 Windows 与 macOS 的验证情况。
- 是否涉及资源版本号提升、`interface.json` 或公告同步。
- 修改 pipeline 时，逐条对照 `CONTRIBUTING.md` 的提交前自查清单。

### 外部贡献者的 PR

- 默认目标分支为 `develop`，因为 `develop` 是仓库默认分支。若 PR 错误地指向 `main`，先请贡献者改目标分支。
- 不接受把 fork 的 `main` 直接合入本仓库 `main`。
- PR 合并后删除来源分支，避免远端分支堆积。

### 发布不变量

分发能否生效只看下面三项是否一致，与 tag 指向哪个提交无关：

| 位置 | 要求 |
|---|---|
| Release 的 tag 名 | 与下面两项完全一致 |
| `pack_all.ps1 -Version` 传入值 | 与 tag 名完全一致 |
| 包内 `assets/interface.json` 的 `version` | 与 tag 名完全一致，且高于上一版本 |

tag 名与包内版本号不一致时，用户端会因为「包内版本没有变高」判定没有更新，MirrorChyan 上传成功也不会有人收到新版本。

### 版本发布

发布分两条路径：测试版（`vX.Y.Z-beta.N`）直接在 `develop` 上打 tag，正式版（`vX.Y.Z`）先合并 `main` 再打 tag。

共用准备：

1. 确认 `develop` 上的内容已完成验证，桌面项目构建通过，必要时跑通 `pack_all.ps1` 的完整打包路径。
2. 在 `develop` 上完成版本号同步：`assets/interface.json` 的 `version` 与 `custom_title`、`assets/resource/announcement/` 的公告文件，以及 `tools/pack_all.ps1 -Version` 的传参必须保持一致。递增规则（PATCH / MINOR / MAJOR）属于维护者约定，未随仓库分发，本节只保证上述四处一致。
3. 把版本号与公告的提交推送到远端（推荐，不是发布的前提）。分发只读 tag 名与 Release 里挂的产物，所以忘记推送不会影响发布；但推送后 `git checkout vX.Y.Z` 才能复现这一版源码，CI 覆盖的也才是发布出去的那份代码。发现忘记推送时直接补推即可，tag 指向的提交不会改变，不需要删 tag 重建。

#### 测试版发布

4. 直接在 `develop` 上打 tag 并推送，不需要 PR。也可以在创建 GitHub Release 时由界面创建 tag，效果相同。

```
git switch develop
git pull --ff-only
git tag vX.Y.Z-beta.N
git push origin vX.Y.Z-beta.N
```

5. 在 `develop` 上执行本地一键打包，并基于该 tag 创建 GitHub Release，创建时勾选「Set as a pre-release」。

```
pwsh tools/pack_all.ps1 -Version vX.Y.Z-beta.N
```

6. MirrorChyan 上传完成后，在 MirrorChyan 后台确认该版本进入测试版频道。若被判定成稳定版，说明这条路径不可用，改回「先合并 `main` 再打 tag」并更新本节。

#### 正式版发布

7. 在 GitHub 上新建 PR，base 选 `main`、compare 选 `develop`，合并时使用 Merge commit，把测试版期间累积的全部改动一次带进 `main`。`main` 已开启分支保护，本地合并后再 push 会被拒绝。
8. 合并完成后同步本地 `main`，在 `main` 上打 tag 并推送。

```
git switch main
git pull --ff-only
git tag vX.Y.Z
git push origin vX.Y.Z
```

9. 在 `main` 上执行本地一键打包，并基于该 tag 创建 GitHub Release，不勾选 pre-release。

```
pwsh tools/pack_all.ps1 -Version vX.Y.Z
```

正式版发布后 `main` 与 `develop` 应当一致；若发布过程中在 `main` 上补了提交（例如公告微调），必须把这些提交合回 `develop`。热修同理，只合回 `main` 会让修复在下一次正式版合并时丢失。

### 紧急热修

热修从 `main` 切出，修完后必须双向合回。

```
git switch main
git pull --ff-only
git switch -c hotfix/<scope>
```

修好后推送该分支，并在 GitHub 上开一个 base 为 `main` 的 PR 合并，然后同步本地 `main` 打 tag：

```
git push -u origin hotfix/<scope>
git switch main
git pull --ff-only
git tag vX.Y.Z
git push origin vX.Y.Z
```

最后把 `main` 合回 `develop`。`develop` 允许维护者直接推送，这一步在本地完成即可：

```
git switch develop
git pull --ff-only
git merge main
git push
```

只合回 `main` 而不合回 `develop`，下一次发布会把旧代码重新覆盖上去，这是双主干模型最常见的失误。

## 常见误区

- 在 `main` 上直接开发，破坏稳定线的可发布性。
- 在本地把 `develop` 合并进 `main` 后直接推送；`main` 要求通过 PR 合并，推送会被拒绝。
- 热修只回 `main` 不回 `develop`，导致修复在下一个版本丢失。
- 把正式版 tag 打在 `develop` 上：正式版必须先经 PR 合并进 `main`，`main` 才是稳定线的发布点。
- 测试版为了打 tag 而先对 `main` 开一次 PR：测试版直接打在 `develop` 上，`main` 只在正式版发布时更新。
- tag 名与包内 `assets/interface.json` 的版本号不一致：用户端会因为版本没有变高而收不到更新。
- 以为「tag 必须指向发布包对应的提交」才能发出去：分发只读 tag 名与 Release 产物，tag 指向的提交只影响源码可复现与 CI 覆盖面。
- 长期不把 `main` 合回 `develop`，两条线逐渐分叉，发布合并时产生大量冲突。
- 使用 `upstream` 远端时误带 push，把提交推到上游的 MFAAvalonia 仓库。
